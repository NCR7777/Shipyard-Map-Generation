## 旧版刷新后恢复关联失败的根因（经审查更正）

旧版 `SV01`、`SV02`、`M11_localFileFlow` 的刷新用例都在 `page.reload()` 之后的第一个断言失败，日志为 `Target page, context or browser has been closed`（行为调研见 scratchpad `p4/old_project_spec.md`）。

- 我用探针（`.cache/probe/probe_handle*.spec.ts`，不进仓库）复现：把一个 OPFS 文件句柄存进 IndexedDB，读出含句柄的记录时整个浏览器进程退出，退出码 `2147483651`（`0x80000003`，Chrome 内部断言失败），无头与有头都一样。
- 审查者进一步对照（scratchpad `rv18/handle_crash.cjs`，每种情形单独一个浏览器进程）：

| 情形 | 结果 |
| --- | --- |
| Playwright `browser.newContext()`（无痕上下文），刷新后读取 | 崩溃 |
| 同上，不刷新、存完即读；或存的是目录句柄 | 崩溃 |
| 手动启动、只加最少参数的 Chrome，经 CDP 新建的无痕上下文 | 崩溃，`0x80000003` |
| Playwright `launchPersistentContext`（普通配置目录），刷新后读取；或关闭浏览器再开 | 正常读回 |
| 手动启动的 Chrome，用它自己的普通配置目录 | 正常 |

- 结论：**崩溃只发生在无痕（off-the-record）上下文**，与 Playwright 启动参数、刷新都无关。旧版刷新用例失败，是因为 Playwright 默认的浏览器上下文就是无痕上下文；用普通配置的真实用户大概率不受影响（真实选择器返回的句柄无法自动化验证，这一点仍存疑）。用户若在无痕窗口里用旧版并关联了文件，刷新后恢复关联就会让整个浏览器退出，丢失全部无痕数据（包括浏览器工程）。
- 本机 Chrome 为 153.0.8010.52，另有已下载待切换的 .54；旧版这些用例 2026-09-14 还能通过，此后 Chrome 更新过，与「浏览器更新引入」一致，但未做版本对照。
- 我最初把原因写成「读回句柄就会崩溃」，并推论旧版会让用户浏览器在启动时崩溃；在普通配置下这不成立，已按上表更正（`localFile.ts` 与测试中的注释同步更正）。

## 范围与改动

- **设计**（`src/app/state/localFile.ts`）：复用内核的 `LocalFileController`（与旧版相同，P0 原样移植）。**文件句柄只留在内存中，绝不写入 IndexedDB**：网页无法可靠判断自己是否在无痕窗口里，而在无痕窗口里读回句柄会让整个浏览器退出。工程在浏览器本地（localStorage）只记住文件名和两个哈希（原始字节、地图内容），不记句柄。
- **每个文件操作属于发起它的工程**：文件操作进行中（包括等待浏览器询问写权限时）拒绝切换工程或打开新地图，并说明原因；操作完成时若显示的已不是那个工程，结果不记录、不显示、不替换地图；内核在忙时拒绝重置，重置改为在操作结束后进行。冲突对话框打开时快捷键不生效（与其他对话框一致）。
- **打开并关联本地 JSON…**：用浏览器的文件选择框选一个地图 JSON，作为新的浏览器工程打开，并与该文件关联。「打开地图…」（文件输入框，支持 zip 与底图图片）保持不变，打开的地图不关联文件。当前工程写不进浏览器、新地图没能打开时，原工程保持原来的关联，刚选的文件不关联到它；仅内存模式下只打开、不关联。
- **保存（Ctrl+S）**：先存浏览器检查点（失败则不写文件），再写回关联的文件；写回前重读磁盘，原始字节与上次写入或读取时不同则不写（见冲突）。写权限在按键当时就请求，之后才等待检查点，免得用户手势在等待中失效。
- **文件另存为…（Ctrl+Shift+S）**：写到新文件（或另一个已有的地图文件）并把关联移过去；目标里有无效内容时不覆盖。浏览器不支持直接写文件时改为下载 JSON。
- **关联原文件…**：把当前工程与磁盘上这张地图的文件关联；文件必须是这张地图（地图编号与坐标框架相同）。
  - 刷新后：工程记得原文件名，状态栏提示「重新选择后才能写回」；保存只存浏览器并提示重新选择。重新选择同一个文件（原始字节与记录一致）即关联，不写入；
  - 文件内容与当前地图相同：直接关联；
  - 其他情况：先询问（「关联内容不同的文件」：取消 / 另存文件版本并关联），确认后把文件中的版本另存为恢复副本，再关联，下次保存用当前地图覆盖它。
- **外部修改**：窗口获得焦点时检查已关联的文件（只读、不弹权限）；保存时也会发现。发现后弹「外部文件已变化」：取消 / 载入文件中的版本（当前地图先另存为恢复副本）/ 文件另存为… / 先保存双方恢复副本 → 用当前地图覆盖外部文件。对话框按每次冲突单独显示：保存过的副本只对应那一次看到的外部版本，外部文件之后又变了，要重新保存副本才能覆盖。外部文件不是有效地图时，只能取消或另存为（内核也拒绝覆盖无效内容）。任何情况下都不会不经选择就覆盖文件或替换地图。
- **升级格式**：升级前另存恢复副本；升级成功后解除与原文件的关联并删去记录（原文件保持原格式），提示用「文件另存为」保存升级后的地图。旧版先解除关联再升级；这里改为升级成功后再解除，升级被拒时关联不丢（文件只在保存时写入，不会在两步之间被写）。
- **状态栏**：已写回 / 有修改未写回 / 正在读写 / 重新选择后才能写回 / 外部文件已变化。
- **文件另存为（仅内存模式）**：写出文件但不关联（保存不可用，关联没有意义）。
- **说明**：帮助面板加入本地文件的约定。

## 设计决定

- 句柄不跨页面保存，代价是每次刷新后要重新选一次原文件；换来的是在无痕窗口里也不会整体崩溃。审查者建议的后续做法：做成可选的「记住文件访问」，只在用户明确开启时使用，启动时不自动读取、只在用户点击时读取，并用普通配置目录（`launchPersistentContext`）做 e2e。我最初设想的「读取前留下标记，崩溃后不再重试」在无痕窗口里无效（标记随无痕数据一起被清掉），不采用。
- 工程与文件的关联记在 localStorage（按工程），不写进工程记录：内核的工程记录格式不变，内核目录与 2d21c16 一致。
- 与旧版的差异：旧版「导入 JSON」会在支持时用原生选择框并关联；新版把「打开地图…」（导入，不关联）与「打开并关联本地 JSON…」分开，打开 zip 与底图图片仍走前者。旧版的「重新载入文件」「写回关联文件」「检查外部变化」合并到保存、获得焦点时的检查和冲突对话框中。

## 复审后的次要修正

- 写入等待期间升级格式，迟到的写入会把刚解除的关联记回来（同一工程，所属工程检查拦不住）：加「关联代次」，解除关联与切换工程时递增，文件操作完成时代次不同就不记录；另外写入等待期间拒绝升级并说明。
- Ctrl+S 会请求两次写权限（按键时一次、写入时一次）：保存改为整个（请求权限、检查点、写文件）是一个文件操作，写入前先等按键时那次请求的结果，写入自己的请求随即得到结果，不再弹第二次。改动时我一度把「等待权限」放到了文件操作之外，重新打开了切换工程的窗口，被扩展后的 e2e 抓到，已改正。
- 两层防护只测到一层：补测「写入等待期间拖入另一张图被拒」「写入等待期间升级被拒」，并断言只请求一次写权限。变异检验：写入前不等按键时的请求、升级不拒绝、打开新地图不拒绝、检查点失败仍写文件，都会失败。「完成时的所属工程与代次检查」「冲突对话框后的快捷键屏蔽」有前一层防护，属于纵深防御，未单独测试。

## 已知限制

- 刷新后需重新选择一次原文件才能写回（见设计决定）。
- 工程与文件的关联记录（localStorage）不会清理；「打开并关联」后若在首个草稿写入前就刷新，会留下对应不存在工程的记录（无害）。
- 直接读写本地文件只在支持 File System Access 的浏览器（Chrome、Edge）中可用；其他浏览器只能导入与导出。
- 外部修改只在窗口获得焦点和保存时检查，不实时监视文件。
- 自动化测试用源私有文件系统的句柄代替真实文件；真实文件的权限弹窗（首次写回时浏览器会询问）未在自动化中覆盖。
