# P3f4 阶段报告：拆出的入口不再关联作业点（通过）

日期：2026-09-26。执行者：主会话。前置：P3f3 已通过，本地提交 4f253ea，已推送 Shipyard-Map-Generation main a1a569e。审查：RV26「修正后通过」（2 项重要、10 项次要）→ 修正后增量复审「通过」（剩 3 项次要，提交前已改，不需再审）。

## 来由

执行者在 P3f3 交付时问了三个问题：作业点留在原节点还是随入口走；浏览器内影像预处理（P3d3）要不要排期；之后的阶段推送是否等指示。用户 2026-09-26 回答：

1. 「服务点留在原节点，入口成为独立节点后断开与原来的服务点的连接，但是不断开与其他的节点连接的道路」；
2. 「继续做」；
3. 「每个阶段通过后都自动推送」。

第 1 条，执行者先按读法 A 实现（清除作业点指向被拆入口的 `accessPointId`，原节点道路不动）。审查 RV26 指出至少有三种读法，且 A 的后果难以逆转、会自动推到公开仓库，应先确认。执行者随后用选择题问了用户，原文如下：

- 题「拆出入口后，入口、作业点、道路三者的关系按哪种做？（前提：入口已沿墙移开 4 m 到自己的节点，作业点留在原路口）」，选项：
  - 「A 作业点断开入口关联 (Recommended)」：作业点留在路口、仍接着原来的路，但不再记为「经此入口」；入口单独在墙上、不接路。代价：编译输出里 18 对「研究接入点 / 研究交接点」不再配对（作业点仍有所属建筑）；这个关联只能撤销恢复，属性栏没有重新关联的字段，需要时另做功能。这是我按你原话实现的做法。
  - 「C 保持现状，仍关联」：与已推送的 P3f3 相同：作业点留在路口、仍接路，也仍记为「经此入口」，只是这个入口本身不在路网上。配对保留，但记录与实际不符（车辆在路口作业，不经过入口）。代码回到 P3f3。
  - 「B 道路跟着入口走」：原来接在路口上的道路改接到入口的新节点，作业点留在原位置、与路网断开。不建议：公共道路端点和转向要移动 4 m；入口又落在公共路口上，建筑仍然不能带着它移动，拆出失去意义；作业点断路，调度到不了。
- **用户答（自填）：「我是要拆开之后自己在页面中重新连接，保持原有道路不变，然后我自己重新添加入口进行连接」。**

执行者的理解与裁定：

- 第 1 条：拆开时断开入口与作业点的关联（读法 A），原有道路不变（排除 B）；之后由用户在页面里自己重新连接：添加入口（P3b1 已有）、从入口画路接入路网（道路工具已有）、把作业点关联到入口。最后一项现在做不到（属性栏没有这个字段，复杂地图上内核也拒绝），写进 P3b2 作为用户工作流要求。
- 第 2 条：确认做 P3d3，排在 P3d2 之后（排期选择，理由见 PLAN）。
- 第 3 条：每个阶段审查通过并本地提交后，自动快进推送到 Shipyard-Map-Generation 的 main（写进 AGENTS）。

## 改动

- 内核 `src/domain/accessSeparation.ts`：
  - 拆出时，凡是 `accessPointId` 指向这个入口的作业点都清除这个字段，其余字段不变；新节点的说明里列出它们的「名称（ID）」（`accessPointId` 不是拓扑字段，拓扑来源记录不到它）；
  - 拒绝条件分两支：经这个入口走内部通道的作业点（`accessPointId` 指向这个入口），**不论归属**，都拒绝（入口是它的通道起点）；本建筑从原节点进入的内部通道（`entryNodeId` 或节点是原节点）照旧拒绝。第一版把第一支也限定在本建筑，没有声明归属的草稿作业点会被放过、通道起点被悄悄删掉（RV26 重要 2），已改。
- `src/app/state/editOps.ts`：成功提示加「原来关联这个入口的 N 个作业点不再关联它」；`src/app/ui/Inspector.tsx`：按钮说明改为「原节点及其道路、作业点留在原处，关联这个入口的作业点不再关联它」。
- `AGENTS.md`：推送一条改为用户授权的自动推送：方法（含 `-m`）、以上一次报告记下的 SHA 核对远端、只快进、仓库公开与推送前检查、`GIT_PUSH_PENDING`、与 paper01 规则的差异。
- `docs/PLAN.md`：P3f4 一节；执行顺序插入 P3f4；P3d3 由提议改为确认并写准排期理由；P3b2 加「作业点关联入口」。`docs/ADR-003.md` 的加注同改。`README.md` 进度。

## 代价与限制

- 属性栏在任何地图上都没有作业点的 `accessPointId` 字段；复杂地图（有路口、转向、资源或规划扩展，真实地图都是）上内核 `updateServicePoint` 改它也被拒（审查者在 4 张 EA01 图上试 18/18 被拒）。在 P3b2 做出「作业点关联入口」之前，拆出后断开的关联只能靠撤销恢复。
- 研究数据中成对的入口与作业点（如 `AP_MR_F_CR012` 与 `SP_MR_F_CR012`）拆出后不再互相引用；编译输出（调度与仿真会读）里这 18 个作业点没有入口，配对只剩名称与新节点说明里的记录。
- 内核的「创建时接路」规则（`connectedPoint.ts`，`CONNECTED_POINT_ACCESS_OWNER`）要求新建的设施节点代理作业点带同一设施的入口；拆出后会出现不带入口的这类作业点（真实地图拆出前 0 个，拆出后 18 个）。校验器不把它当问题。
- `accessPointId` 对节点代理作业点的影响：接路与路径检查用的是作业点自己的节点，不受影响；但复制作业点时会连带它的入口（`commands.ts:116-118`），动入口时作业点算作受影响对象（`commands.ts:264`），断开后这两处不再连带。
- 拆出后的入口不在路网上（P3f3 起如此），要用户自己画路接上。

## 冲突与裁决

- **与内核创建规则 `CONNECTED_POINT_ACCESS_OWNER`**：规则针对新建，校验器不报；用户明确要拆开后自己重新连接，裁定接受这一中间状态，由 P3b2 的「作业点关联入口」补上重新连接的手段。
- **清除范围超出原话**：用户说「原来的服务点」，代码清除所有指向这个入口的作业点，包括不在原节点上的。理由：入口拆出后不在路网上，任何作业点经它都不成立；真实地图上这类为 0。执行者裁定。
- **与 paper01 AGENTS「阶段通过后……推送当前工作分支」**：用户的「每个阶段通过后都自动推送」理解为推 Shipyard-Map-Generation main（此前的推送都是它），不推 d4/rasc（推它会在论文仓库新建分支并带出 D4/RASC 研究提交）。Shipyard main 上只有每阶段的目录快照，逐阶段的开发提交在本地。写入 map-studio AGENTS。
- **P3d3 的排期**：排在 P3d2 之后不是硬依赖，真正的前提是 P3d2 开工前要定的内核沿革做法（PLAN 已写准）。
- **ARRIVAL 条件的实际范围**：同时写了 `accessPointId` 与 `entryNodeId` 的设施作业点会触发错误级的 `INTERNAL_ENTRY_CONFLICT`，内核在未通过校验的地图上拒绝任何命令，所以这部分放宽只改变 `inspectAccessSeparation` 在这类本就无效的地图上给出的原因，没有误伤。没有声明归属的草稿作业点（只有警告、地图有效）是实际受影响的情况，现在被拒绝。
