## 已发现问题、修复与复核

### R01：重复长道路导致连接校验成本被严重低估（阻塞，已解除）

原实现按“服务点数量 × 道路数量 + 内部弧数量 × 转向数量”计算诊断预算，却对每个内部弧重新计算整条道路长度。合法的交替正反向重复序列可在 JSON 大小和预算内触发大量重复折点遍历。

审查时给出的风险构造为一条含 8000 个折点的道路、100 个服务点各引用 2048 个重复弧：原预算约 20 万，几何处理却可达十亿量级。该大型构造用于说明静态计算成本，**没有运行会长时间占用环境的大型输入**。

核心负责人修复：

1. 新增 inspectServiceConnections，同次批量检查共享一个临时道路长度缓存，同一道路只派生一次。
2. 单点诊断也在本次调用内缓存重复道路；缓存不写回地图，不跨地图版本保存。
3. 预算纳入实际道路折线段数量，超限返回 SERVICE_CONNECTION_COMPLEXITY_LIMIT，不展开每个服务点诊断。

独立复核读取了以上实现，并实际执行：

    npx vitest run tests/unit/M2A1_connectionCost.test.ts

2026-09-09 17:42 本轮结果：退出码 0，1 个测试文件、2 项测试通过。回归验证两服务共享重复内部道路时 roadLength 总计调用一次，另验证超限组合在展开服务诊断前拒绝。原阻塞解除。

### R02：单独调用诊断时未直接报告设施/入口悬空引用（非阻塞，已修复）

外层 validateMap 原先已有设施与入口引用检查，因此共享导入没有接受悬空引用的漏洞。但独立调用服务诊断时，对节点和区域检查悬空、对设施和入口遗漏，接口表现不一致。

核心负责人补充了 facilityId、accessPointId 不存在及入口设施归属冲突的直接诊断。本代理只读复核确认，仍保留原外层校验，不以诊断替代 Schema。
